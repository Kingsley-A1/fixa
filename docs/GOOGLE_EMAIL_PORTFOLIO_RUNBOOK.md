# Fixa: Google sign-in, minimal email, work portfolio — controlled rollout
Version: candidate · 2026-10-30 · depends on R1–R3 draft PR #2
Owner: Bespoke Technologies

## The three capabilities
- **Identity:** Google OIDC authorization code + PKCE, state/nonce, signed short-lived flow cookie, verified Google ID token, unique Google subject. Reuses Fixa's existing signed HttpOnly application session and password accounts. No access to Gmail, Drive or Contacts.
- **Email:** Small, transactional Resend delivery only; one-time SHA-256 token, 20-minute expiry, 60-second request throttle, user-initiated POST confirmation, profile approved/rejected notices. No campaigns.
- **Portfolio:** One optional work sample per real completed/ready assigned job; max three photos; browser-reencoded WebP <=2MB each; private Blob storage; customer-consent attestation, server-side owner checks and manual moderator approval. Public profile has 3 clean 4:5 image cards and an optional full-work page. No likes, feeds or auto publishing.

## Google Console
1. Create/select a Google Cloud project, configure OAuth consent branding/privacy info and client type Web application.
2. Authorized redirect URI: `https://fixa.bespoketech.com.ng/api/auth/google/callback` (exact match). For preview OAuth testing, add only the specific secured preview deployment origin, if necessary.
3. Copy client ID/secret to Vercel production environment; deploy. OAuth sign-in UI appears only if both exist and AUTH_SECRET is valid.
4. For existing password users, sign in with password first and select **Connect Google account** from technician profile. Email must match and be verified by Google; automatic email-based account takeover is forbidden.
5. Verify CSRF state, nonce, PKCE, one-use flow cookie, signature, email_verified and provider subject. Test revoked/cancelled consent and mismatched address. Google-only account users may sign in even if public registration is closed; new user creation still requires `ENABLE_REGISTRATION=true`.

## Portfolio acceptance
- Only an explicitly assigned technician can create a draft from their own real READY/COLLECTED job. The source job data stays private.
- An image is never public just because it was uploaded. It is stored in a *private* Blob store and served by `/api/work/media/[id]` only to its owner, platform admin, or for approved work attached to an approved published profile.
- Upload accepts a browser-reencoded, non-animated WebP with no EXIF/XMP/ICCP chunks, verified server-side. A moderator still checks faces, identifiable private screens, serial labels and misleading images.
- Technician explicitly attests customer permission at submission; this is **not yet an independently obtained customer consent record**. Establish a stronger consent workflow before expanding beyond a moderated pilot.
- Rejected samples can be edited/resubmitted. Images can be removed from draft. Deleted images are removed from storage when available; orphan cleanup should be monitored.
- Cards: one cover image, short repair title underneath, no status badges, likes, rating overlays or branding. Maximum three recent cards on profile; complete portfolio on separate route.

## Security and remaining launch gates
- DB-backed tests: account linking and user collision, session persistence, phone/password sign-in after migration, concurrent one-use email tokens, cross-tenant media and work-sample access, admin-only moderation, card visibility on rejected/suspended records.
- Durable login, signup, OAuth start, verification email, upload and review rate limits at the edge/infrastructure; account recovery and session revocation procedures.
- Privacy/terms and public image consent policy, takedown/dispute/appeal pathway, identity and skill claims reviewed.
- Penetration/CSRF and SSRF review, Blob API version compatibility, audit logs, corrupted image and storage failure tests, backup/restore rehearsal, mobile browser QA.
- **No automatic merge to main or live launch until these gates pass.**
